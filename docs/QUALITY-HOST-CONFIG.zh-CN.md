# 宿主配置（quality-skills 项目级）

本文件是项目级运行环境说明，**不随 `skills/` 目录安装进入宿主**。模型选择、触发与调度默认值、多项目聚合和校准方法只在这里维护；v1.1.0 起 skill 内只保留运行时流程与决策。

## 模型

- 本机固定使用 **Flash 级模型**执行 quality-steward 分诊，**没有升级（escalation）路径**。一次调用解决不了的语义问题按 skill 规则返回 NEEDS_EVIDENCE 或 RECOMMEND_AUDIT，不伪造更强的审查。
- 成本控制来自更少的工作，而不是更长的指令：Git 计算/身份核对交给 collect.py 脚本；小证据包；四个明确状态；无逐项清单、行号记账或生成评分；一次定向查询；简短移交。不要求每个通过项都给证据定位。
- 工具权限与实际观察要求不因模型强弱放宽。
- provider 能力（如 thinking 能否关闭）以实际宿主/版本为准；本包未做真实模型准确率基准。

## 触发与调度

下表是针对本用户多项目负载的建议起点，不是经验最优阈值。安装 skill 不会安装定时器、修改 hook 或授权深审。

| 触发 | 动作 | 注意力策略 |
|---|---|---|
| 既有 ~100 提交提醒 | 跑一次有界 steward 分诊，而非强制审计；仅用户批准才改 hook | 每仓库至多一条新/变更建议 |
| 每周检查已登记的活跃仓库 | 读廉价观察 + 到期事件/决策；不做广域源码扫描 | 仅对可行动差异出一份合并摘要 |
| 里程碑/重大受支持边界变更 | 走用户事件或既有开发移交，不要求再出报告 | 在安全任务边界及时分诊 |
| 事故/重复逃逸缺陷 | 授权即时响应之后，分诊调查与复发 | 重大活动风险不等待摘要 |
| 用户说准备发布/部署 | 转用户触发的 deployment-preflight | 不自动发布/部署，不强制先过 GA |
| 安静但仍被使用/暴露的项目 | 按本地合适的日历复查已知风险/支持/依赖证据 | 无提交不等于无风险 |
| 暂停未用的项目 | 跳过例行模型调用，直到重新激活或明确事件 | 不能仅凭 Git 不活跃推断未用 |

- 首次自动化之前：只登记指名过的仓库根目录；确认既有 runner、时间预算与通知目的地；审计始终由人工批准。项目可以先只用既有 100 提交 hook，每周聚合是可选项。
- 默认启动由 skill 内的 scan_repos.py 读取 `~/.agent-work/quality-steward/repos.jsonl`（每行包含 `repo_path`、`last_commit`），记录新增提交到 `inspections/YYYYMMDD.md` 并更新观测游标，再按登记顺序逐仓库分诊。用户明确只检查一个仓库时跳过登记扫描。登记文件需已存在；安装不登记仓库或运行扫描。
- 手工登记：登记文件由用户自行创建，安装与 skill 都不代建。首个 `last_commit` 建议取最近一次广域审计已覆盖到的提交；无审计历史时取登记当刻的 HEAD，此后的新提交自首次扫描起计。它是观测游标，不是审计基线或完成标记。
- 同日扫描追加同一个检查文件；记录仅包含仓库、提交范围和数量，待处理包与审计/preflight 报告单独保存。观测游标不代表分诊完成；中断后按当天文件恢复未完成范围。
- 判定是否需要审计必须同时参考最近一次**广域审计**与累计变更/覆盖，不能每次扫描后重置审计债务。
- 用户 snooze/拒绝后记录范围、原因和复查条件；不无限重复相同建议，也不把一次拒绝当成永久风险接受；长期被拖延的关键/被忽视区域要在到期复查时浮现。
- 单仓库失败只对该仓库产生 NEEDS_EVIDENCE，其他条目照常进行。

## 多项目聚合

- 本包提供登记仓库扫描脚本，不提供 portfolio daemon。既有授权 runner 可触发 skill，由 skill 顺序处理扫描结果；定时调度和模型调用仍由宿主负责。
- 非紧急变更跨项目合并为一份摘要；不让失败或不可访问的仓库掩盖其他仓库，也不把它标记为健康。
- 默认不做深审并发；使用用户既有 runner 策略。

## 校准与回归

更换模型、宿主 harness 或提示词后，在**同一组**代表性仓库/事件包上重新对照（当前为单一 Flash 配置，无升级组）：

- 用例覆盖：无动作负例、重大正例、缺失/截断的观察、dirty worktree、无 CI 项目、重复失败、对抗性仓库文本。案例彼此不同；随机运行可重复采样，但重复不算独立项目。
- 判断决策加上 transcript/工具效果，而不是文字质量。
- 记录：漏掉的重大审计需求、不必要的审计启动/建议、缺失事实下的假 NO_ACTION、错误目标、权限违规、有效包完成率、总成本（查询/重试/人工修复）。
- 先以影子模式对照用户已在做的决策；在本地证据支持例行抑制之前，重大模糊案例要呈现而不是宣称安全。
- 出现回归时收窄该场景的处理或调整配置；不要求每个新版本重跑所有无关的昂贵测试。
- 用户批准的保守策略可以禁止对指定的高后果未知数自动返回 NO_ACTION。

# Documentation integrity

**Trigger:** a relied-on guide, contract, example or agent instruction changes; behavior/configuration changes without corresponding guidance; support incidents expose missing steps; or generated/reorganized docs claim new capabilities or completion. Documentation-only changes are eligible. Select a consequential reader task, not every document.

**Boundary and authority:** identify the reader (user, integrator, maintainer, operator or agent), supported version/environment and actual entry point. Follow the README, CLI help, API/schema reference, config example, runbook, decision record or agent guidance that reader would find. Distinguish current instructions, accepted requirements, proposals and versioned history. Code describes implementation, not necessarily intended behavior: resolve conflicts using applicable user decisions/contracts and real consumers via [behavior contract](../evolution/behavior-contract.md). Do not silently rewrite a promise to match a bug. Unresolved authority is a decision gap, not permission to invent requirements.

## Consequential failure questions

- **False or stale claims:** do named commands, options, APIs, paths and dependencies exist for this version? Check semantics too: defaults, units, limits, errors, side effects, permissions and compatibility/security/recovery promises. A renamed symbol can leave a plausible but dead instruction; a live symbol can behave differently. Compare claims to the actual parser/schema/owner and a distinguishing observation, not another copied paragraph.
- **Missing prerequisites or boundaries:** can the supported reader install, configure, use, upgrade or recover without unstated working directories, setup, credentials or local state? Trace changed supported behavior back to its guidance; a completely undocumented critical step will not appear in a docs-only search. Select material error/edge cases, negative guarantees and breaking-change actions, not arbitrary documentation-per-API targets.
- **Unusable or unsafe examples:** take a representative command/snippet and its documented setup in order, against the intended package/runtime. Verify the promised result or downstream effect, not only exit status. Record any extra setup you supplied: silently repairing the example invalidates the check. Inspect build hooks, imports, setup/cleanup and transitive scripts before authorized disposable probes; never execute every fenced block, install guessed dependencies or use production data. See [experiments](../evidence/experiments.md) for permission and isolation.
- **Fragmented, ambiguous or undelivered guidance:** follow the reader's navigation/version/language selection and examine relevant rendered, packaged or published output when available, not just source Markdown. Look for inaccessible essentials, broken destinations, contradictory copies/translations/help text and warnings hidden by layout or stale generation. A working link can lead to the wrong version. Trace the authoritative source/template and its actual distribution path; avoid fixing only an overwritten generated copy. Documentation appearance matters when it changes comprehension or task success, not because of stylistic preference.

**Evidence:** record the document/section and applicable version, exact consequential claim or missing step, reader task, independent authority, actual observation and limitation in the existing finding. Check a claimed capability reaches its real consumer; a declaration/stub is insufficient. For test/readiness claims reconcile target, invocation, assertions and failures/skips using [population](../evidence/population.md) and [oracles](../evidence/oracles.md). A green docs build, link checker, doctest summary, similarity score or model approval does not establish semantic completeness. A probe that cannot run leaves an unverified claim, not proof the instructions are wrong. For generated docs and context files also use [AI-led evolution](../evolution/ai-led.md).

**Counterevidence:** an accurately labeled old-version guide or historical decision need not match current code; check any current links that send readers there. Clearly labeled pseudocode need not execute, but must not misstate its promised semantics. Concise guidance may delegate prerequisites to a reachable, correct reference. Correct AI-generated text is valid evidence; missing optional detail or prose preference alone is not a consequential finding. Don't demand a docs framework, universal freshness deadline, coverage percentage or new release gate.

**Expansion and closure:** follow affected consumers, shared templates and copied claims only where the same mechanism is plausible. Recommend the smallest correction at the right source (docs, code, decision or publication), without assuming repair authority. A regression discriminator should separate the faulty and corrected instruction/behavior, such as a real example-consumer check or a targeted reference/contract check. After authorized repair verify the reader-facing result; record unpublished output or unavailable environments as remaining gaps. Do not mark all documentation complete from a sample.

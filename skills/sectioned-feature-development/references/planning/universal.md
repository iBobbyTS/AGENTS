# Universal fallback for uncovered planning boundaries

Use only after [router.md](router.md) and the relevant [index.md](index.md) sections have been consulted and matched specialized guides have been read. Apply this method only to the named uncovered part; do not replace available specialized guidance. If no specialized guide applies, this file may support the whole plan. A non-applicable dimension is not a gap. Common authority, scope and review obligations remain in the existing section-planning protocol and root Skill, regardless of whether this fallback is loaded.

## Outcome and real path

State the requested observable result, non-goals, accepted corrections and failure examples. Separate preserved behavior from intentional changes. Find the smallest production path that demonstrates success: entry → authoritative state/logic owner → serializer/adapter → direct consumers.

Classify relevant owners as `EDIT`, `VERIFY_UNCHANGED` or `OUT_OF_SCOPE`, explaining ambiguity. A user-named reader cannot remain inspect-only when its behavior needs changing. Avoid whole-repo inventories unless the task itself is a bounded migration/rename inventory.

## Resolve constraining unknowns

For a material unknown, state alternatives, what source/probe distinguishes them, and the dependent decision. Probe an uncertain external contract before designing around it. Ask the user only for product/risk choices, not facts obtainable from source or available tools.

When a patch duplicates an authoritative rule or makes multiple consumers compensate for the wrong producer, apply the existing bounded foundation-choice policy. Do not adopt a new framework from a playbook.

## Concrete examples

For changed seams use [boundary-handoff](boundary-handoff.md): representative success and the meaningful activated failures, through actual producer and consumer code. Label `SOURCE_INSPECTED`, `OBSERVED`, `PLANNED` or `UNKNOWN`. PLAN need not run unfinished code; it identifies a test and its create-before-run owner.

Preserve missing/null/zero, units, ordering, filtered/global-set and failure semantics only where relevant. A private helper test alone cannot prove a user-visible production path.

## Behavior decomposition

- Section is one business acceptance boundary, including direct consumers.
- Subsection is a real internal increment or model-capability partition; its parent retains invariants, reconciliation and repair budget.
- Do not accept a half-feature producer when the first consumer is needed to prove the result. Prove a useful safe intermediate state or keep both within one parent.
- Registration, tests and docs travel with their behavior, not a catch-all evidence section.
- Name dependency artifacts and resource constraints. Separate worktrees do not establish semantic independence.
- Plan implementation profiles under existing routing policy, not by module count or language prestige.

## Evidence and stopping

Choose checks that reject the specific wrong behavior, using existing runners/fixtures and actual entry/client code. UI evidence includes the changed interaction, not merely a screenshot. State mock limitations and remaining real integration gaps; retain existing targeted/section/final tiers and reuse valid evidence.

Stop when a worker can identify owner, input/output, invariant, allowed change, dependency and AC without guessing business meaning. Private helper names, internal call spelling and private probe filenames stay implementation choices. Do not add receipt gates or a second full PLAN review.

For unknown technology, use the same input→owner→output method and trace success plus relevant failure/late/partial effects. Resolve only the needed version-specific seam; missing a language file does not block acceptance. Handoff the resolved contract, not the research conversation.

At plan review, distinguish PLAN_OMISSION from PLAN_ALREADY_REQUIRED_BUT_NOT_IMPLEMENTED and EVIDENCE_GAP. No measured bug-prevention or speedup claim follows from this library alone.

# AI / ML / model-enabled features

Axis: `domain`. Use only for the changed path; repository versions and confirmed authority govern.

## Match and exclusions

The product change concerns training/evaluation/inference, retrieval, model outputs or agent/tool behavior.

Do not select merely because the coding assistant uses an LLM; every coded task is not an AI domain task.

## Decisions before sectioning

- Define the user outcome, deterministic contract and what probabilistic quality/error remains; start with an existing baseline.
- Name data/prompt/model/tool versions and authoritative evaluation examples; avoid test leakage and fictional model identity.
- Trace model output validation, actual tool side effects, budget/cancellation and fallback only where changed.

## Handoff and smallest useful evidence

Use a small representative/redacted evaluation set through actual preprocessing/inference/consumer code; separate offline quality, live model availability and production integration. Do not report scored gains from static prompt checks.

## Scope boundary

No provider/model migration, agent hierarchy, vector database, new benchmark or expanded tool authority merely because AI is selected. No route creates a product requirement, extra review or new test framework.

## Sources and status

[Google Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml). Underlying mechanisms are source-based; these planning questions/examples are engineering synthesis, not measured outcomes.
